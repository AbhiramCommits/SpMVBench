# SpMVBench error analysis

All numbers below are the **measured** values in `results/accuracy.csv`, produced
by `./build/bench --validate` against the SciPy float64 reference generated by
`tools/reference.py`. The reference vector `x` is deterministic and has entries
spanning roughly `1e-6 .. 1e6` with random signs, precisely so that rows with
mixed-magnitude terms expose cancellation.

## Accumulation modes

For every matrix and every CPU kernel we ran:

| tag | values | accumulator |
|-----|--------|-------------|
| `fp32/fp32` | float | float |
| `fp32/fp64` | float | double |
| `fp64/fp64` | double | double |

plus a Kahan-compensated CSR variant (`csr_kahan`) as an extra accuracy
datapoint. All CSR decompositions (`csr_scalar`, `csr_vector`, `csr_merge`) and
`ell` are numerically identical for a fixed mode, so the table reports the CSR
numbers.

Every `fp64/fp64` CSR result agrees with SciPy to **exactly 0** relative error
(the library and SciPy perform the identical summation order; reported as 0.0 in
the CSV). Block/format kernels (`bcsr`, and the OpenMP `spmm_csr`) differ only by
the order of summation and stay at or below ~3e-12 max relative error in fp64.

## Reading the numbers

**Input rounding dominates `max rel err`.** Casting values and `x` from fp64 to
fp32 perturbs each product by ~`u32 = 2^-24 ≈ 6e-8` *of that product's
magnitude*. Because the reference `x` spans 12 orders of magnitude, a row whose
nonzero output `y_i` is small relative to `sum_j |a_ij x_j|` (cancellation) shows
a large *relative* error even though the *absolute* error is tiny. This is why
`fp32/fp32` and `fp32/fp64` have comparable `max rel err` for several matrices:
the largest relative errors come from rounding the inputs, not from the
accumulator.

**The L2 relative error is the meaningful aggregate, and fp64 accumulation
helps it.** Switching the accumulator from float to double while keeping fp32
storage reduces the L2 relative error by roughly 2x to 13x, e.g.
- banded_100k: `5.28e-08 -> 3.55e-08`
- powerlaw_skew: `4.35e-07 -> 3.27e-08` (the worst fp32 accumulator case)
- uniform_random: `7.55e-08 -> 3.28e-08`

## Scaling with row nnz

The only matrix here with long rows is `powerlaw_skew` (row lengths 1..8000,
CV ≈ 5.3). It also has the largest fp32/fp32 error: L2 relative error
`4.35e-07` versus `5.28e-08` for `banded_100k` (row lengths 3..5). With fp64
accumulation both drop to ~`3e-8`, i.e. **the accumulator is the limiting factor
for long rows, while for short rows the input rounding (which fp64 accumulation
cannot fix) dominates.**

## Kahan compensation

Kahan summation on the fp32 accumulator recovers part of the fp64 benefit
without widening storage:

| matrix | csr fp32/fp32 L2 | csr_kahan fp32/fp32 L2 | csr fp32/fp64 L2 |
|--------|------------------|------------------------|------------------|
| banded_100k | 5.28e-08 | 5.04e-08 | 3.55e-08 |
| powerlaw_skew | 4.35e-07 | 4.71e-08 | 3.27e-08 |
| uniform_random | 7.55e-08 | 4.83e-08 | 3.28e-08 |
| diag_dominant_small | 5.52e-08 | 5.24e-08 | 3.53e-08 |

On the long-row `powerlaw_skew` matrix Kahan cuts the fp32 L2 error by ~9x,
close to the fp64 accumulator, while preserving fp32 storage.

## Error bound

The classical bound for a dot product of length `n` computed in precision with
unit roundoff `u` is

```
|y_hat - y|  <=  gamma_n * sum_j |a_ij x_j|,     gamma_n = n u / (1 - n u).
```

With `u = u32 = 2^-24 ≈ 5.96e-08`, and using the measured
`max_row sum_j |a_ij x_j|` (from the committed reference `x`):

| matrix | max-row `sum|a x|` | row nnz | `gamma_n * sum\|a x\|` | observed fp32 max abs |
|--------|--------------------|---------|------------------------|-----------------------|
| banded_100k | 3.57e+06 | 5 | 1.06e+00 | 2.68e-01 |
| diag_dominant_small | 5.56e+06 | 8 | 2.65e+00 | 4.51e-01 |
| powerlaw_skew | 3.19e+08 | 8000 | 1.52e+05 | 3.40e+01 |
| uniform_random | 3.18e+06 | 20 | 3.79e+00 | 3.68e-01 |
| tiny_3x3 | 1.52e+05 | 2 | 1.81e-02 | 8.21e-03 |

The observed maximum absolute errors are **below** the bound in every case, by
factors of ~4x (banded, tiny), ~6x (diag), ~10x (uniform) and ~4500x
(powerlaw). The bound is a worst case that assumes every rounding error is
maximally adverse and aligned; real errors partially cancel, so the bound is
pessimistic, most dramatically for the long heavy-tailed rows of
`powerlaw_skew`.

## Notes and limitations

* `max rel err` for `spmm_csr` (OpenMP) reaches 0.14 on `uniform_random` while
  its `max abs err` is only `1.6e-06` — again a near-zero output component, not a
  real loss of accuracy. The L2 relative error there is `8.8e-08`.
* `bcsr` (4x4) is the only fp64 kernel with non-zero error (`~3e-12`), because
  its block accumulation changes the summation order relative to SciPy.
* These measurements are CPU-only on this machine. The GPU kernels are
  source-complete but were not measured here (see the README's hardware section).
